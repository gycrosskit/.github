# 组件抽离路线图

本计划来自三端接入项目中已经存在的平台能力。下列首版表格是历史记录；当前仓库分类和精确发布版本以[组织首页](../profile/README.md)与各仓库 README 为准。接入项目在对应远程依赖与工程契约验证后迁移并删除旧实现，真机业务验收另行记录；不把业务页面、账号、品牌配置和服务端协议搬进组件库。

| 顺序 | 仓库 | 公共能力 | 留在接入项目的内容 | 验收重点 |
| --- | --- | --- | --- | --- |
| 1 | `permission` | Android、iOS、OpenHarmony 的相机、麦克风、前台定位权限状态、申请和设置页返回后的恢复 | Manifest/权限声明、申请时机、业务提示文案 | 首次拒绝、再次拒绝、受限状态、宿主销毁和迟到回调 |
| 2 | `scanner` | 三端二维码图片解码；Android/iOS 相机预览与识别；OpenHarmony ScanKit 系统扫码 | 扫码框样式、二维码业务解析、扫码后的导航和服务端操作 | 相机暂停与释放、权限拒绝、取消、相册二维码、重复回调 |
| 3 | `media` | 三端选图、拍照、按需压缩和保存到相册；返回图片字节与元信息 | 上传策略、业务图片大小限制、页面提示 | 原图与压缩、取消、并发请求、临时文件、鸿蒙大图传输上限 |
| 4 | `location` | 三端单次定位、权限与服务状态、超时、缓存时效和精度过滤 | 业务定位精度要求、地址展示、业务字段绑定 | 取消、超时、服务关闭、粗略定位、缓存过期 |
| 5 | `system-actions` | 拨号、外部 HTTP(S) 链接、应用设置和商店详情跳转 | 商店上架地址、业务白名单、成功/失败文案 | 非法输入、系统是否受理、多品牌应用标识 |

`scanner` 与 `media` 可以使用 `permission` 的能力，但各库保持独立发布；扫码库不包含图片选择器，媒体库不包含二维码识别。鸿蒙宿主按上述职责注册各组件 Module，不聚合权限与定位实现。系统扫码界面与自定义相机预览不同，各平台实际入口和体验以对应 README 为准。

| 仓库 | KMP / 其他远程依赖 | 鸿蒙 HAR |

| [`location`](https://github.com/gycrosskit/location) | JitPack `0.1.0` 已通过 Android/iOS 独立消费 | `@gycrosskit/location-native@0.1.0` 已提交 ohpm 审核 |

这些构建和远程消费结果不等于真机验收。ohpm 查询到版本并能从 registry 安装前，不把 HAR 写成已上架；真实接入项目仍需按平台逐个迁移和回归。

已有的 `toast` 优先验证并接入现成远程版本；`compose-webview`、`live-sdk`、`koin-ohos`、`stately-ohos`、`mmkv-ohos` 继续维护现有仓库。认证、支付、直播会话和扫码业务流程涉及接入项目的账号、厂商配置或服务端协议，保留在宿主；原生 SDK 接入机制由对应现有组件负责。

## 当前收尾范围（2026-10-04）

本轮收尾固定为 19 个机制迁移包，复用已有组件仓库：diagnostics 的异常/日志执行、文件与导出、系统报告解析、网络记录、可选通知传输；debug-tools 的安全存储与摇动；system-actions 的剪贴板/分享、UIKit、系统观察与窗口执行；compose-webview 的窗口桥和两种数据清理；scanner 的反馈与预览；permission、location、media、toast 的类型化 Kuikly 接入；wechat 的可信请求持久化；Live/客服的原生 IM 与共享 SDK 身份边界。窗口由两个现有组件配套完成，计为同一迁移包。

工程退出条件是这些机制都完成发布和实际远程消费，接入项目删除对应重复主体，保留业务/UI/品牌/协议/生命周期薄接线，并通过需要的三端构建和定向回归。版本、消费者证据与渠道限制归各组件验证文档；仅创建仓库、JitPack 显示 ok 或编译成功不能代表全部结项。

业务 Session、Repository、导航、页面、资源、签名、厂商账号、后端协议和当前业务小工具继续归接入项目，不因为可以拆分而新增通用 utils 仓库。以后新增能力属于新需求，不重新打开这份固定范围。

真机业务验收由使用方完成并单列。OHPM 审核、同版 Release HAR 下载/安装、生产 HAP 构建分别记录；不能把审核接受写成 Registry 上架，不能以旧正式包验收新 API。

## 宿主复核后的四项跟进（2026-10-07）

后续源码复核继续复用现有仓库：`compose-webview` 补齐 OHOS 资源缓存/网站数据清理，`live-core` 提供 62 项兼容表情编码/解码与中立 OHOS KLIB；宿主接入已发布 `system-actions` 的复制/文件分享，以及 `diagnostics-ktor` 的关联、有界、脱敏网络采集。没有新增第 15 个功能仓库，OHOS 中立表情协议也不代表提供直播、IM 原生 SDK 或 PiP。

表情资源与编辑、Debug 准入、私有文件限制、取消/销毁、业务 UserSig 脱敏和 Release 日志策略仍由宿主决定。组件发布与公开消费证据见[持续集成门禁](持续集成门禁.md)；宿主补丁整合和实际三端构建状态归其唯一组件接入文档，不能以组件发布代替宿主已接入。

## 每个组件的实施顺序

1. 从真实调用方确定最小 API 和平台范围，核对第三方依赖及许可证。一个接入项目足以启动抽离；不虚构尚未实现的平台能力。
2. 在独立仓库实现公共能力与必要的宿主接线，按[组件开发](组件开发.md)保留平台生命周期、取消和错误语义。README 使用中文，说明平台差异与接入步骤。
3. 分别验证实际需要的 Android、iOS、OpenHarmony 构建及设备行为；再用独立消费工程从远程产物编译和运行。缺少设备验证时明确记录，不宣称该平台已验收。
4. 按[发布流程](发布流程.md)发布 KMP/JitPack、需要的 Swift Package 和鸿蒙 HAR/ohpm；各渠道分别确认可下载、可安装。接入项目切到已验证版本后，才删除本地重复实现。
5. 新仓库创建时启用 Issues、保护 `main`，并按[Issues 与迭代流程](Issues与迭代流程.md)持续处理真实接入反馈。
