# 组件文档规范

README 是第三方接入入口，以中文说明当前发布的能力；GitHub 没有强制的 README 格式。本规范沿用 [GitHub README 指引](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes)，避免消费者先阅读本地发布过程才找到安装方法。

## README 必要内容

1. 用途：解决什么问题，业务账号、鉴权和 UI 等由谁负责。
2. 支持范围：实际发布的平台、模块、最低系统要求、匹配的工具链；未验证的要求如实标注。
3. 安装：固定版本的公开坐标及必要仓库。分别说明 Maven/KMP、Swift Package/Git Pod、HAR；版本可能不同。Git Pod 不等于已发布 CocoaPods Specs，GitHub Release HAR 不等于 OHPM 上架。
4. 最小使用：与当前 API 一致的 imports、初始化、调用及释放；业务输入注明由宿主提供。
5. 必要边界：权限、可信输入、异步回执、取消、资源释放和平台缺失能力。不可用平台不写成空成功；编译通过不表示设备业务验收。
6. 文档与维护：接入指南、开发验证、Release、Issues、许可证和上游来源；反馈只收集脱敏复现信息。

结构允许按组件规模调整，不为满足目录增加空章节或虚构徽章。fork 必须区分上游坐标和适配坐标，并说明实际维护分支；上游默认分支不能冒充 OHOS 发布版本。

## 架构与调用图

根 README 在安装步骤前给出“架构与调用流程”，让接入者先辨认入口与职责，再查具体坐标。使用 GitHub 支持的 Mermaid 代码块，与源码一起评审：

- 架构图：画实际模块、公共入口、平台实现与宿主职责。箭头注明依赖、调用或数据方向；用途分组图明确说明分组不表示依赖。
- 关键流程图或时序图：选择一次最常见的操作，标出初始化、返回结果、取消与释放。异步事件不要画成同步决策，平台缺失能力不要画成成功路径。
- 核心类图：只保留理解 API 所需的少量真实类型，区分继承、字段引用和使用关系。函数不要伪装成类，创建参数不要画成所有权；省略完整方法清单。

每张图配一两句阅读说明，核心类型链接到当前仓库的相对源码路径。fork 只画本仓库实际维护和发布的适配范围；组织首页使用用途地图和接入流程，不复制所有组件类图。优先使用简短节点、常见 Mermaid 语法，检查语法、渲染和源码对应关系；文档改图无需重新发布二进制版本。

## 详细文档

优先复用已有文档；复杂平台接线放 `docs/接入指南.md`，源码构建、发布命令和验证方法放 `docs/开发与验证.md` 或现有专门文档。验证历史留在已有记录中，README 只说明当前边界并提供入口。

仓库文档使用相对链接，随代码和版本一起评审。HAR 内的 README 保留自身版本、平台、安装和关键限制，以公开仓库链接指向完整说明，避免复制整份接入指南。公开接入路径不依赖维护者本机的绝对路径或私有业务仓库。

## GitHub Wiki

[GitHub Wiki](https://docs.github.com/en/communities/documenting-your-project-with-wikis/about-wikis) 支持较长的使用文档，公开仓库可使用；默认由仓库写权限成员编辑。是否启用属于仓库设置，启用不等于已有 Wiki 页面。

当前以 README 和仓库 docs 为唯一版本源，暂不另建相同内容的 Wiki。需要可视导航时，Wiki 可链接到具体版本的仓库文档；只有明确需要独立维护长篇手册时再迁移内容，并同步移除原来的重复版本。文档修改不自动授权开启 Wiki、提交或推送。
