# 统一远程源码验证

本机只运行 Python 3 标准库和已登录的 GitHub CLI；源码测试、Android 编译、iOS/OHOS Kotlin 编译与 CI 已配置的链接均由现有 GitHub-hosted runner 执行。统一入口不调用 Gradle、Swift、Hvigor 或本地构建脚本，也不创建提交、推送代码或发布产物。

## 使用

从本共用仓库运行，或用脚本的绝对路径从任意目录运行：

```sh
# 查看接入的 14 个组件，不联网
python3 scripts/remote-verify.py --list

# 只读核验全部入口及 main SHA，保存计划，不触发构建
python3 scripts/remote-verify.py --all --dry-run

# 全部 14 个组件的默认远程验证，并发 2
python3 scripts/remote-verify.py --all

# 也可选择当前改动涉及的组件
python3 scripts/remote-verify.py compose-webview toast diagnostics

# 全部 14 个组件；需要更保守时串行执行
python3 scripts/remote-verify.py --all --parallel 1

# 验证已推送的任务分支；该分支必须在所有选中仓库存在
python3 scripts/remote-verify.py compose-webview --ref codex/example
```

第一次使用先完成 `gh auth login`。读取公开仓库和运行状态需读权限，触发 workflow 需要对应仓库的 Actions write 权限。脚本通过 `gh api --hostname github.com` 复用登录，不读取、保存或输出 token。使用 [REST API 2026-03-10 的 dispatch 回执](https://docs.github.com/en/rest/actions/workflows#create-a-workflow-dispatch-event)直接取得 run ID，不按“最新运行”猜测身份。

默认结果目录为 `~/.cache/gycrosskit/remote-validation/<UTC批次时间>/`，可用 `--output /绝对路径/新目录` 指定；已有目录拒绝覆盖。入口打印目录中的 `results.json`，同目录的 `results.md` 可直接查看组件、完整预期/实际 SHA、状态、结果、Actions 链接及失败 step。每次状态变化更新回执，任一组件失败时批次最终退出码为 1，仍执行其他已选择组件。全部通过退出 0。

## 验证范围与身份

| 类型 | 组件 | 触发参数 |
| --- | --- | --- |
| 源码/发布 CI 分开 | compose-webview、live-sdk、jverification、wechat、debug-tools、customer-service | `regression.yml`，`warm_native_cache=false` |
| 合并 CI | toast、location、media、scanner、permission、system-actions、sound、diagnostics | 同上，并明确 `version=""` |

Koin/Stately/MMKV 的 OHOS 适配不在首批范围，入口拒绝未知组件。首批只做完整源码验证；指定已发布版本的精确远程消费者继续使用组件现有发布验证 workflow，不混入本批次的源码结论。

入口先核验所有选中组件的 workflow 为 active，再冻结远程 ref 的完整 SHA。每个组件触发前再次检查 ref，已移动则记录 `ref_changed`，不启动该组件；其他组件继续执行。触发时分支仍可能变化，因此结束后必须满足实际 SHA、`workflow_dispatch` 事件和 workflow 路径均与计划一致，才可能算成功。

成功还要求 `changes/contracts/android/native` 四个 job 均成功，并拒绝这些 job 中实际执行了 `Explain lightweight completion` 的运行。合并 CI 的发布 job 在源码模式下轻量完成属于预期，不影响源码结论。JSON 保存全部 job 和 step 的结论；细节与公开日志使用 Actions 中已有的 7 天诊断 artifact。

远程 ref 的验证不包含本地未提交或未推送代码。普通 main push 的轻量检查、Native 缓存预热、源码验证、精确发布消费者和宿主真机验收是不同证据，不能相互替代。

## 并发与恢复

并发单位是“一个组件的完整 workflow”，queued 和 in-progress 都占槽；workflow 内既有 Android/Native jobs 可并行。默认并发 2，`--parallel` 仅接受 1 或 2；新批次和恢复回执均拒绝超过 2。通过本机共享文件锁限制同一台电脑只能有一个统一入口批次运行；不同 Codex 会话共用此锁。

这是本机统一入口的批次限制，不能约束其他电脑、GitHub 手动触发或 PR 自动 CI，不是组织全局锁。GitHub 自身的 runner 队列和并发配额仍生效；不修改各仓库已有的 concurrency 或 max-workers 规则。

关闭终端或 Ctrl+C 不自动取消 GitHub 已启动的运行，也不重试失败构建。未完成回执登记在本机共享目录；下一次新批次会被拒绝，要求先恢复：

```sh
python3 scripts/remote-verify.py --resume /绝对路径/批次/results.json
```

恢复沿用原回执的组件、ref、预期 SHA 和并发数；有 run ID 的组件只查询已有运行，pending 组件在空槽位继续触发。dry-run 计划不能恢复为实际构建，需要重新运行正常命令。

若 POST 网络超时，或程序在 POST 和回执写入之间退出，状态保留为 `dispatching`，禁止自动重发。先到对应仓库 Actions 确认：已启动则把准确 `run_id` 和 `queued` 状态补入该项后恢复（URL 自动生成）；明确未被接受才改为 `pending`。无法确认时保留回执，避免重复占用 runner。查询 run/jobs 失败同样保留已有 run ID，恢复只读重查。

## 维护与最小验证

共用实现只维护 [`scripts/remote-verify.py`](../scripts/remote-verify.py)，不复制到 14 个组件。组件新增或 CI 合同改变时同步脚本组件集合、输入分组与本页；不引入新的协调服务或第三方 Python 依赖。

```sh
PYTHONDONTWRITEBYTECODE=1 python3 scripts/test-remote-verify.py
git diff --check
```
