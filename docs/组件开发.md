# 组件开发

## 确定组件边界

1. 先说明组件面向的宿主、平台、最低系统版本、公共 API、依赖和许可证；只承诺实际实现并验证的平台。业务账号、文案、本地化、页面和凭据由宿主提供时，在 README 中写清楚。
2. 复用当前仓库的模块和构建方式。KMP 共用逻辑放在 `commonMain`；Android、iOS、OpenHarmony 的 SDK、View 和文件系统能力留在对应平台边界。不要为了尚不存在的复用点增加一层接口。
3. 修改公共 API 或依赖坐标时，同步检查各平台变体、传递依赖和消费方编译。原生 Swift Package、HAR 与 Gradle/KMP 产物分别说明，不能把其中一种当作另一种的验证结果。

## 实现与验证

- 先读现有实现和调用方，找最小的共同修复点；保留上游 fork 的来源与许可证说明。
- 先按变更范围完成最小本地编译、测试与消费验证，涉及真机问题时先打包到设备复验，再创建 MR/PR。已接入 CI 的 14 个功能组件随后按[统一远程验证](统一远程验证.md)补充检查，默认并发 2、上限 2。跨平台组件检查实际影响的平台；缺少 SDK、签名或设备时先说明阻碍，不默认先提 MR/PR 或发 RC，不把编译成功写成设备验收。
- 测试围绕公开行为选择正常、边界、失败及生命周期场景；涉及取消、重入、迟到回调或并发时，检查旧请求隔离、资源释放及工作线程异常能否使测试失败。源码文本检查只证明接线或结构，不能代替运行时断言。
- Simulator runner 退出码不等于断言已执行完毕，须检查本轮唯一结果、保留失败日志并拒绝旧 PASS；新 SDK 的生命周期要求由测试壳满足，不能跳过原断言。系统冷启动就绪与组件行为分别计时：例如真实 WebKit 首次请求曾等待系统 AppSSO 配置 27 秒，可用独立真实请求确认环境就绪，失败仍阻断，不放宽原行为断言。
- 用独立消费工程检查公开坐标和 API；不要只依赖本仓库源码或 `publishToMavenLocal` 的结果。
- 根 `README.md` 以中文说明用途、平台、真实依赖坐标、初始化、边界和验证范围。上游英文内容可以另存或链接，但应明确上游坐标与本 fork 坐标的区别。

README 与详细接入文档按[组件文档规范](组件文档规范.md)组织。发布版本与远程验证按[发布流程](发布流程.md)执行。

## 原生能力与 Kuikly 接线

- 对外先说实际产品和发布渠道：Kuikly 是 UI/接线产品，KMP 是底层 Kotlin Multiplatform 构建技术；JitPack 提供 Maven/KLIB，ohpm 提供原生 HAR。不要把 KMP 描述成额外 UI 产品，也不要把 JitPack 写成 Android Jetpack 或把 ohpm 写成其他渠道。宿主依赖升级与 View 注册、登录、前后台/注销接线分别说明，不能笼统承诺“只加依赖即可”。
- 共用请求、事件、状态机和原生会话放在核心模块，Kuikly 在薄平台边界接线；不新增独立 CMP UI 产品。Kuikly Compose 所需 compiler、腾讯 compose 和共用 runtime 继续保留，不能按 `Composable` 或 `androidx.compose.runtime` 名称清删。独立消费者应拒绝第二套 JetBrains/AndroidX UI、foundation、material，依赖图不完整时必须失败；消费编译、Android D8 和 Native 链接分别核对，不能只看源码 import。
- Kuikly 的 View 方法异步返回。导航、来源授权等需要同步判断的规则先下发到原生，不能等待 Kotlin 事件返回后再阻止请求；方法回调使用 JSON 对象，不返回裸字符串。
- Kuikly 的 `createEvent()` 只创建事件对象；框架在工厂返回后才注入 `pagerId`，不能在工厂内调用会访问 Pager/Render 的 `register()`。需要自动注册的事件放在 View 挂载后，回归至少用真实 Kuikly 执行事件创建与初始化顺序，避免替身预先填充页面 ID 掩盖闪退。即使只有某平台发送该事件，写在 `commonMain` 的注册逻辑仍影响其他平台，不能凭注释认定它们不受影响。
- Bridge 授权使用原生提供的真实 frame/来源，或由原生投递到指定可信文档的独占通道。当前页面 URL、JS 自报来源和随机 Token 都不能单独证明调用者身份；导航、输入变更、隐藏和销毁后撤销通道与未完成回调，旧实例不得给新请求重新授权。
- 平台 SDK 缺少某项能力时，明确返回不支持并记录最低系统版本。不用空成功实现承诺三端一致；系统 View、厂商 SDK、房间协议和设备行为分别核验。

## 本轮抽离形成的检查点

- 通用执行机制下沉到现有组件：有界缩略图、提交等待/取消、原始 SDK 监听与多订阅回放不归宿主；业务同意、品牌、服务端凭据/结果、路由和窗口 owner 留宿主。迁移时清除旧状态，不能只搬参数转发层。
- CMP UI 退役后反查真实消费者：三端 Kuikly 使用已有 Module，删除仅旧 UI 使用的业务 Platform 实现与闲置状态；原生 owner 的注册、历史数据、系统回跳和资源释放仍保留。每 Renderer receiver 不等于第二个进程 SDK；原生类名不同也不自动构成未对齐。不因 callback/requestId 结构相似就合成通用请求框架，须保留系统弹窗、外部回执与页面终态各自的释放条件。
- 测试精简先确认同一行为已有执行覆盖，再删重复矩阵、旧 API 替身和纯源码写法断言。公共 Module、原生 receiver、厂商 client 的相似场景覆盖不同边界，不机械去重；平台测试壳和取消/旧回执/归属用例不能因无真机而删除。
- Pod 验证 helper 以 `templates/ci-build-kuikly-render.sh` 为源，同步组件副本并逐字节核对；选择 Module 时让其 podspec 决定 Renderer，不能额外强制旧版本。单独 Renderer 探针固定 `2.29.1`，历史远程 tag 保留自身依赖；用现有 `scripts/test-ci-helpers.py` 核对实际 Podfile 的本地/远程/旧 tag 路径，避免下一次模板同步带回冲突。
- 微信提交等待按请求 ID/kind 管理，不引入全局 busy；REQUESTED 只代表受理并立即释放本次提交等待，最终回执关联继续保留。验证连续无回执重试、旧超时/取消/回执与后继请求交错，不能以 iOS 单笔候选替代 VERIFIED，也不能把转账页回执当到账。
- 图片回归应执行实际解码器：Android Robolectric legacy BitmapFactory 可能把非法数据当默认 Bitmap，图片输入/预算测试使用 Native Graphics；历史测试图片须确认编码可解压。取消继续抛出，不能被“解码失败返回 null”吞掉。
- 异步生命周期：回调完成与消费协程恢复之间仍可能取消或撤销同意；返回凭据前再校验 owner/generation/consent。多阶段操作在每次 `await` 后校验当前请求，不能只在 SDK 回调里校验。未同意、关闭和取消的请求要立即结算，避免创建永远不能满足回调/超时条件的 pending。
- 原生公开类型：Kotlin 公开 API 若暴露厂商类型，应提供相应编译依赖；只内部使用的 handler 保持私有。HAR 公共签名中的厂商 UI 类型需从组件入口导出或明确要求宿主直接依赖。用独立产物消费发现此类问题，不用源码依赖掩盖它。
- ArkTS 真实编译：TypeScript 转译或 SDK 声明替身不能替代 Hvigor/ArkTS。按选定工具链核对构造字段声明、可抛类型和完整监听接口（含其要求的旧别名）；Live 的 API22/6.0.2 编译曾因此失败，不能把普通 TypeScript 写法直接视为可发布 ArkTS。`LocalStorage` 初值也须显式声明类型；通过 WindowStage 传参时，页面 `@Entry` 需启用共享 storage，不能只在 Node 替身中证明传入了对象。
- 跨端事件语义：初始化快照、人数刷新与真实状态变化分开；首次未禁言或他人进房不能生成“解除禁言”通知。按 SDK 回调到公共状态、文案的完整链路逐项对照；成员消息复用公共语义与序号逻辑，观察在公共 joined 确认后启用，避免初始状态先发后丢。
- 媒体实例归属：首帧、播放状态和 View 绑定须核对同一播放器、订阅目标及实际渲染。业务进房隐式创建的媒体实例有解码，不证明独立播放器有画面；相同播放协议在新旧 SDK 中也可能分别订阅主播原流或混流，先用相同参数的原生最小 Demo 核验，不据日志中的任意首帧判定接入通过。
- 系统功能接线：共同按钮不证明各端能力已接入；请求入口、宿主真实状态观察与后台续播必须连通。`Unsupported`、缺少宿主回调和系统拒绝应分清原因，不能一律解释为权限问题；PiP 请求受理、预布局提示和真实 STARTED 状态分别处理。小窗音画不代表完整体验通过，还须验证主应用其他页面可操作、展开复用原会话及关闭只释放直播宿主。
- 多窗口归属：新增 Activity/UIAbility 前沿全部窗口策略调用方核对 privacy、常亮及网页全屏的实际 owner。同一 WindowStage 共用 controller，跨窗口必须隔离；旧 Renderer 持有旧实例结算，不能重新解析到后继窗口。SDK 若只按 Ability metadata 存前后台，宿主须聚合同名实例或过滤旧代，不能让旧实例后台/销毁覆盖新实例前台。进程账号及 SDK 不随局部宿主退出注销，前后台恢复也须查询实际媒体 owner，不能用“应用任一窗口前台”替代。
- 可选 SDK 的账号生命周期：直播、客服等能力分别判断是否安装，不能因某个 SDK 缺失跳过另一个的 prepare/reset。窗口消失、停声和返回登录页不证明腾讯账号已注销，还须核对实际 reset 回执及随后重新登录；单测应覆盖仅安装一个能力的组合。
- 浮窗比例：显式透传公共布局的横竖参数和内容宽高，不能让系统按迁移中的原生节点尺寸推导；只迁移 Surface 时，还须防止公共预布局把源节点撑成整屏后再压进浮窗。画布比例与源视频比例分开，按产品合同选择 Fit/Fill，恢复和释放时解除临时布局约束。对比旧包、源码、实际 Surface 尺寸及设备截图，不能把裁剪、留边和非等比拉伸混为一谈。
- 鸿蒙最近任务：独立 UIAbility 会产生独立任务卡片；`excludeFromMissions` 仅系统应用有效，普通三方应用不能用此配置隐藏仍存活的直播任务。`removeMissionAfterTerminate` 只负责关闭后的任务移除。需要单任务体验时，须先验证单 Ability 窗口/PiP 方案，不能把多 Ability 带来的体验差异归因于直播 SDK。
- 返回应用的生命周期：区分从最近任务恢复、点击桌面入口、外链和系统 PiP 展开。先核对系统启动 Intent、任务栈和宿主销毁日志；Launcher 清栈触发的离房不能归因于 SDK 断流。配置回归只防止规则倒退，真实系统启动栈仍须设备验收。
- Kuikly/ArkUI 节点：从实际 Render HAR 核对注册器、基类和节点工厂。Render 2.28 的自定义 View 需实现 `createArkUIView(): ComponentContent<KuiklyRenderBaseView>`，按真实 UIContext 创建节点；ArkUI 观察由实际状态 owner 建立，不能用普通字段初始化 `@ObjectLink` 冒充订阅。内部导出的厂商节点锁定精确版本并写明兼容风险；源码/消费者编译与真实挂载、首帧分别验收。
- Kuikly OHOS 工厂归属：`2.29.1` 的 View/Module creator 按类型进程全局覆盖，不能捕获最后注册的 PageDelegate、Ability context 或窗口 controller。实例 `init(instanceId)` 后按实际 Renderer 绑定依赖；需要现场验证“原页面→独立直播→退出→原页面新建 H5”，不能只验冷启动单页。仅将 `getLastWindow` 改成 WindowStage resolver，无法修复工厂闭包捕获错误 owner。
- 微信等待策略：比较宿主是否实际注入可选 store，不能把组件支持持久化当成三端已经启用。若一端重启恢复旧授权/分享/转账，会占住共用 pending 槽；不得按 `busy` 清空当前请求来补偿。三端采用进程内等待时保留 owner、取消和回跳校验，明确进程被杀后不自动续接业务；修改策略不得删除旧记录或伪造成功。
- 本地 HAR 消费准入：根 `oh-package.json5.overrides` 可覆盖 entry 的 `file:` 替换，不能仅记录传入的 HAR 路径或版本就声称修复入包。安装后核对实际解析来源及源码摘要，并在关键 SDK 修复时核对 HAP 内编译实现；若仍是 Registry 旧实现，设备失败不能作为新代码的验收结论。签名与依赖恢复也需逐文件校验。
- 微信发送与回执：网页分享与转账发送互斥只持续到 SDK 受理，不得等微信最终回执才能重试；微信未登录或直接返回可能没有回执。保留有界、按 requestId/transaction 关联且不阻塞新请求的记录，旧回执和取消不能清除新请求；不保存业务领取状态。回归至少覆盖连续两次无回执提交、65 次以上提交、旧回执与新授权交错及跨 Renderer 重试。iOS 缺少转账 transaction 时如实交付 `UNATTRIBUTED`；受理或确认页成功不能作为到账证明。可选持久 store 清除失败仍须保护可信等待，不能伪造失败诱发重复提交。
- 微信多 Ability context：唯一 SDK 不代表永远沿用首次 Ability。每笔操作前由真实调用方刷新 context，并在请求开始时固定该 context；异步图片解码、临时文件与 SDK 提交共用这一快照，后继 configure 不能改换已开始的请求。需对比 Main 和独立直播的实际拉起状态；`busy` 尚未进入 SDK，不能据此诊断厂商拉起失败。
- 页面取消与 SDK 清理：页面 `finally` 的 scope 可能已取消，普通 `scope.launch` 不会执行注销/撤销等待。使用明确的不可取消清理边界并让后继 attach 等待完成；回归“打开微信后返回→其他方式登录→转账”，验证旧授权取消而非仅清空本地监听。不得据此全局取消其他 owner 的分享或转账。
- Kotlin/Swift 文件错误：Swift 会调用的文件 API、构造器和 factory，按实际可抛异常声明 `@Throws`，确认生成的 NSError 接口可被宿主处理；编译成功不能证明 Swift 能捕获异常。
- 最低系统版本：检查实际依赖的实现与所用 API，不只看组件自身源码和 compileSdk。例如 Android API 24/25 不能使用 `java.nio.file.Files` 的移动实现，应复用可用的薄平台边界并针对真实行为验证。
- 能力如实描述：原生音频预缓冲不等于完整下载或离线可播；各平台崩溃采集机制和投递时间不同；微信回执缺少 transaction 时不能伪造关联 ID，转账页面返回不能作为到账证明。限制写入中文 README，业务与服务端契约留在宿主。

## 功能与平台文档

每个组件库以 `docs/功能与平台差异.md` 维护当前功能合同，README 前部给出 core、原生能力与 Kuikly 的职责摘要并链接到该文档。已退役的 CMP UI 标明旧版本边界，未发布候选不能冒充已发布能力。文档目录与各库入口见[组件文档索引](组件文档索引.md)。

- **真实分层**：列出实际模块、包与公开入口。core 说明公共模型、策略和平台能力；原生与 Kuikly 分别说明 UI、桥接或宿主消费方式。没有独立 UI 模块就明确写出，不为凑层级虚构模块，也不因复用 core 判定 UI/行为相同。
- **逐功能矩阵**：列出公开 API/设置、默认值和回调/取消边界，分别核对实际提供的 Android/iOS/OpenHarmony 入口。Kuikly Compose 属于保留能力；排除项单列，不算通过或失败。数据存储、注入等基础库按真实消费方式填写，不编造 renderer API。带版本的历史 CMP 验收保留原事实，不转记为当前 Kuikly 验收。
- **差异分类**：区分组件未实现、OS/SDK 已证实边界、宿主必须提供的输入，以及未验证项。写清触发输入、SDK/OS 范围和源码依据；未做设备测试不能写成“不支持”，仅找到接口也不能写成“行为已通过”。
- **基线与验证**：标明源码基线 commit、核查日期、是否包含未发布修改；将源码实现、编译/契约回归、模拟器/真机、远程产物消费分开。当前发布坐标不自动包含源码候选功能，不把旧验收记录当作候选新行为的证明。
- **测试对应关系**：功能页的验证节用简短表格列出行为、测试源码入口、实际执行目标和未覆盖范围；开发验证文档保留可执行命令。区分本轮实际重跑与复用的既有结果，说明替身、模拟器及厂商服务边界；同一共享用例跨目标执行不重复算作新增用例。
- **同改同更**：公共 API、默认值、错误码、生命周期、平台实现、原生 SDK 或 UI 入口变化时，在同一变更中同步功能文档、README 摘要和受影响的当前接入指南。先修正相互矛盾的描述，再增加文档；不要复制完整矩阵到多个文件形成多个状态源。
- **保留历史**：带日期/版本的发布与验收文档记录当时事实，不改写成最新能力。历史文档与当前能力不同时，在入口标明历史范围并指向当前功能合同；上游文档保留来源，明确哪些扩展或平台未由本 fork 发布。

文档修改至少检查相对链接、模块/API 名称、状态分类及 `git diff --check`。只有文档变化时无需重复运行全量代码测试；引用既有验证必须写出其精确范围。
