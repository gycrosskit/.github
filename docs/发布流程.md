## OHPM 操作入口

接手 Live、Wechat 的 OHPM 发布时，先读受管 CI 固定提交 `3df827ddc7bb8e6ec8349eb9cbe05ddd4b949158` 的[OHPM 发布与新会话接手](https://gitee.com/shanxi-hanning-network/sxmqlive-ci/blob/3df827ddc7bb8e6ec8349eb9cbe05ddd4b949158/docs/组件独立执行.md#ohpm-发布与新会话接手)（OHPM 能力已由 MR !141 合入 CI `dev`）。2026-10-30 已完成受管发布器入口迁移与两组件原 apply 的只读查回，未发起组件发布或公开消费；旧 Jenkins release guard 仍阻止两组件的 `ohpm`。执行前核对安装回执与 publisher/store/cutover 三份策略一致；现行入口使用无参数 sudo 与固定服务 UID，兼容已核验的旧生产者及既有 apply journal。具体命令、固定身份与接手字段以上述文档为准，其他组件仍沿各自已验收的发布入口执行。

- `har` 是 GitHub Release 归档，`ohpm` 才是官方 Registry 提交；必须分别执行和记录。固定 HAR 已发布不能代替 OHPM 已提交。
- 发布前核对包名/版本、Tag/源码、冻结候选摘要、原 Store/run 和执行身份。`PLAN_ONLY` 不验证发布凭据可访问，本机构建成功也不授予 OHPM 发布身份。
- 现行发布器只用管理员绑定的固定身份，不读取个人 `~/.ohpm` 或候选提供的凭据路径。身份不可访问时核实管理员维护的执行入口，不要求业务用户提供发布码或私钥。
- Live、Wechat 先用 `ci.py component-ohpm prepare --send` 接收冻结候选与零提交 `PLAN_ONLY` 原件，首次提交使用 `ci.py component-ohpm publish --apply`；已提交后用同一入口的 `query` 沿原 handoff/apply run 查回，`resume` 仅按原 journal 的恢复门禁接续；外部写入结果未知时先只读查询，不能恢复 PLAN_ONLY、换版本标签催审或另起发布覆盖原记录。完整参数以上述固定 CI 文档为准。
- [个人中心通知](https://ohpm.openharmony.cn/#/cn/personalCenter/notifications)用于查看审核结果。服务端受理、审核上架、精确版本安装、真实 ArkTS 消费编译分别记录；上架后仍核对下载字节及工具生成的锁文件。

## 任务说明、状态与产物

三个共享 Job 及本轮手动对应步骤都须区分输入、职责、输出和验收范围：

| 任务 | 输入与职责 | 输出及验收边界 |
| --- | --- | --- |
| verify | 精确源码 SHA，或显式指定的已公开版本 | 源码编译/回归，或独立公开版本消费；不生产发布候选，不回填另一类源码结果 |
| package | 精确构建源码、版本与工具链，真实构建新候选 | 冻结归档/来源/摘要并私有消费；不代表公开或 Registry 可安装 |
| release | 已冻结候选、真实来源与不可变 Tag | 同字节公开写入及查回，再执行公开下载与真实渠道消费；审核受理、上架、安装、编译分别记录 |

控制端的 repo/Tag/元数据与状态查回是小任务，不与 SDK 重构建混为同一阶段。候选私有消费和公开消费承担不同信任边界；公开版本复验不重复整套源码检查，真实消费编译/链接也不能作为冗余删除。

每轮索引逐组件、逐渠道记录实际版本、源码/Tag SHA、producer 与 execution CI/helper、构建链接、产物说明、SHA256、精确地址及状态。Jenkins `Run URL + artifact/` 是验证报告和暂存候选入口，公开 Release、JitPack 坐标、OHPM 包版本及 Pod/SPM Git Tag 是各自的交付入口；未发布计划不能标成可下载。Native 源码渠道仅冻结 receipt 时明确写“源码渠道”，不称 SDK 编译通过。Job description 同步显示当前阶段、范围、实际身份、候选生产者和本轮产物入口。

| 状态 | 含义 |
| --- | --- |
| 待执行 / 检查中 | 尚无本轮完整结果；排队与执行分别记录 |
| 候选已冻结，未发布 | package 的归档/receipt 已验收，公开渠道尚未完成 |
| 公开上传已确认，消费待验收 | 已取得实际写入及远程原件确认；不等于安装或编译通过 |
| OHPM 待审核 / 待上架 | 服务端接受提交后仍未完成 Registry 查询、下载、安装与 ArkTS 消费 |
| 公开消费已确认 | 当前渠道的远程身份、字节及所需消费者全部通过；不代替其他渠道或真机验收 |
| 失败 / 外部结果未知 | 保留原始错误与 journal，注明失败阶段及已完成部分；未知写入先只读查回，不能重发猜测 |

阶段耗时单列工具准备、候选复制、节点排队、编译命令、公开写入、就绪及公开消费。命令墙钟时间包含依赖解析，不能称纯编译时间；并行和嵌套阶段不能相加。优化效果须在同工具链、同制品身份下做实际对照，缓存供应成功不等于已证明命中或提速。

## Fork 鸿蒙适配发布

以下 Fork 发布规范仅作历史保留，当前三个 Fork 不再安排新发布。原流程按[Git Flow](GitFlow与提交规范.md#fork-鸿蒙适配流程)晋升，先通过[适配与兼容验证](统一远程验证.md#fork-鸿蒙适配验证)，再发布所维护的上游版本与鸿蒙修订组合。当前版本格式沿用各库既有合同，同时记录官方基线 tag/SHA、Fork 修订和工具链；不与自有功能组件统一版本，不覆盖官方坐标或已有标签、归档及 Registry 版本。

1. 迁移后从 `dev` 经评审与集成验收 PR 到 `main`，核对最终源码树并冻结发布 SHA。尚未完成分支迁移的库继续使用已登记且实际存在的适配稳定线，不能从纯上游 `main` 发布鸿蒙候选。本轮不迁移或发布三个 Fork。
2. 使用固定 CI 的既有 verify/package/release Job 和实际登记渠道。package 绑定最终源码 SHA，构建完整所需 Maven 归档，核验 publication、metadata、许可证和真实摘要，并执行私有消费；旧候选摘要只作历史证据，不能套给新构建。KMP 多平台产物按实际合同保持完整，不因仅修改 OHOS 就留下指向缺失 Android/iOS 文件的 metadata。
3. release 从准确成功的 package producer 取得同一冻结字节，核对版本、源码/标签、CI/helper 和摘要，再按现有 JitPack/Release 或实际 Native/HAR 渠道发布。若必须增加仅元数据的提交，分别记录归档生产 SHA、标签 SHA、树差异和同字节证据；有源码变化则重新验证、构建，不重标旧收据。
4. 发布后从精确公开坐标重新下载、校验并执行独立消费者，覆盖所声明的平台及依赖身份；失败或外部结果未知时保留 journal，只读查回或按现有恢复协议接续，不盲重发或覆盖同一版本。只有实际存在的 Native/HAR/OHPM 渠道才验证，不为三个基础库统一增加渠道。
5. 公开消费验收后记录结果与未覆盖范围，稳定修复回流 `dev`，确认无活动依赖后收尾临时分支和 Worktree；发布 tag、上游来源、许可证、制品与持久证据保留。

## 发布前

先完成相关轻量检查及统一 Jenkins 编译、回归和消费验证；涉及真机问题或设备验收时先本地打包安装复验，再创建 MR/PR。Review、CI 通过后才合并、发布。本地受阻先报告，不为验证接线默认提前发 RC；任务内临时源码消费不能当作公开仓库消费通过。仅文档修改执行相应轻量检查。

Jenkins 或发布脚本有变化时，先 Review 调用方、渠道合同、恢复路径和最小回归，再启动真实发布。固定 CI SHA 与内嵌 runtime 摘要须一起从该提交的 canonical renderer 生成，部署前比较完整脚本与现有参数、profile、trigger 和 XML 外层；部署后回读实际 Job，核对 `load` 前的 guard、归档中的 runtime 字节及精确脚本审批。Jenkins 的审批摘要为 `SHA512('groovy:' + script)`，不能用裸文件的 SHA512 代替。首次 Run 再核对实际 CPS main/loaded script，不能只凭配置 SHA 更新成功认定入口可运行。

Groovy 动态生成 Python 或 shell 时，检查实际生成后的字节，不能只解析原模板；在真实工作目录权限、账号、标签和 JDK 条件下先验最小入口。新增网络读取先做真实隔离环境的短检查，再执行昂贵构建；只读请求的有限重读不能变成构建或发布重放。发现失败先定位并补能复现的回归，保留原失败，再准入下一轮。进度分别报告“代码及针对性检查通过”“完整 CI 通过”“已部署”“代表任务已验收”，不能合写成“优化完成”。

发布前还须对完整渠道集合执行无写入计划检查，核对历史 journal、恢复父 Run、公开与 draft 坐标、服务账号凭据访问，以及历史证据的保留窗口。已知的加载前失败只能由精确脚本、完整执行图和无发布副作用证据识别；未知失败继续阻断，不能删除历史 Run 或放宽门禁绕过。CLI 预演不代表已发布，网络、服务端审核和真实消费者仍按发布后的实际结果验收。

1. 先查询远端 Release、Git tag 和 ohpm Registry/提交记录，确认候选版本未使用；源码或 README 的“未发布”不能替代远端事实。再确认实际发布分支、提交、不可变的 Git 标签、模块坐标、Gradle 版本、Swift Package/podspec 版本、`oh-package.json5` 版本。Koin、Stately 在专项迁移前的鸿蒙适配不在默认 `main`，以实际适配线及迁移验收登记为准。
2. 按项目现有入口构建。JitPack 环境无法完成的 macOS/iOS/OHOS 构建先在相应平台完成，打包到与标签同版本的 GitHub Release；下载时校验 SHA-256，不使用可变的 `latest` 归档。
3. 检查 Maven POM、Gradle Module Metadata、平台变体和引用的 AAR/KLIB/JAR 文件。若 JitPack 把来源或 metadata 变体指向不存在的文件，先确认原因，再使用 [`jitpack-metadata.py`](../templates/jitpack-metadata.py) 模板同步所需仓库的修正脚本；不要无条件删减变体。debug-tools、customer-service 的根 `metadataSourcesElements` 也被改写为普通 JAR，与 `metadataApiElements` 地址相同但校验值不同；模板移除该来源变体，保留实际编译需要的 metadata API 与平台运行时变体。Compose 的空 Resources ZIP 也可能被 JitPack 改写为不存在的普通 ZIP；模板先检查全批 ZIP，仅在只有目录、零实际文件时裁剪资源变体及其 root available-at。即便实际文件为零字节也拒绝裁剪，必须先完成可发布的资源渠道。
4. HAR 发布前检查包内 `LICENSE`、含当前版本的 `CHANGELOG.md`、带精确安装命令的 `README.md`；`oh-package.json5.author` 沿用已通过发布的对象格式（`name` 加公开 `url`，或合法 email），不能只填作者名称。执行真实 `assembleHar` 和 `ohpm prepublish`，再按[OHPM 操作入口](#ohpm-操作入口)由已验收的受控身份提交。`ohpm publish` 接受提交只代表进入审核；上架后还需查询并安装验证。

Native Module 的 Swift receiver 复用 `ci-build-kuikly-render.sh <绝对构建目录> <Pod/Kuikly> [仓库名 精确tag]`：源码门禁从当前 checkout 安装 Pod；Release 传精确 Git tag 验证远程 Pod。一次构建组件 Pod 及其固定 Renderer SDK，返回同一 Products 目录供 KMP consumer 链接，不再重复单独构建 Renderer。单参数模式保留旧版本的 SDK-only 验证。Pod 仅装配原生接收端，不打包第二份 Kotlin framework/runtime。

Native 下载缓存沿用受控 Jenkins 的实际合同，不再调用旧 Actions 的 warm_native_cache dispatch；历史预热测量见[CI 优化与评审计划](CI优化与评审计划.md)。发布计时分别记录本地锁等待、归档构建、PR、runner 等待、public 就绪/校验和 Android/Native consumer，不把排队时间算作编译耗时。

评审前明确冻结源码、版本、文档与归档 checksum，分别记录原生产者和后续 checksum 提交。源码变化按新提交验证；正常合并同 tree 或仅 checksum 元数据变化，可在核对实际 lineage 和原字节后复用既有源码/候选收据，不能把旧构建重标为新 SHA。历史 Actions 曾按整个 PR 相对 merge-base 的差异判定并取消旧流水线；该行为不作为当前 Jenkins 自动重构建冻结归档的依据。

main 因发布新增 checksum/来源元数据后，须经正常 PR 从 `main` 回流 `dev`，核对实际合并内容，再冻结下一轮源码或候选，不能把旧 dev 当成已包含发布历史。本轮其余 13 仓已通过正常 PR 合并回流，仅涉及 24 个文件、26 行新增、零旧行删除；连同此前 Web/Media，15 仓均已回流，postmerge 已逐仓核对 main/dev 同树。纯发布元数据回流不覆盖旧 Tag/归档、不伪造 SDK 重建；若含源码变化，仍按新源码验证。

预构建库复用 [`jitpack-install-prebuilt.sh`](../templates/jitpack-install-prebuilt.sh) 和 metadata 模板，`jitpack.yml` 传入仓库名。每个库的 `release-checksums.txt` 保存已验证的 `Tag SHA256`；未发布版本没有校验值时应直接失败，不使用假 SHA、可变归档或本地自建 Maven。metadata 修复传入当前库的路径，避免改动其他已安装组件。

归档 staging 使用空的任务目录，复用 [`check-maven.py`](../templates/check-maven.py) 检查组名、版本、精确 publication 集合、POM 许可证、平台、实际产物、大小和四种哈希。异构多模块项目显式传入完整 publication CSV；Koin/Stately 使用 `--jvm-only`，MMKV 使用 `--license BSD-3-Clause`。本地归档的 module/POM/变体文件必须具备且通过 MD5、SHA-1、SHA-256、SHA-512 sidecar 校验；SNAPSHOT 按 Maven metadata 解析时间戳文件。metadata 改写后重算 checksum；回归入口为 `python3 scripts/test-jitpack-metadata.py` 与 `python3 scripts/test-check-maven.py`。

- metadata 正规化与 checker 在 macOS 发布前执行；安装器只校验 SHA 并解包相同字节，不在 JitPack 默认的旧 Python 环境重复改写。
- macOS 归档使用 `COPYFILE_DISABLE=1 tar --no-xattrs`，核验没有 `._*` AppleDouble 成员或 xattrs，避免 Linux 把 sidecar 当 JSON。
- 预发布使用不可变 `0.x.y-rc.N`，GitHub 标记 prerelease；明确记录经消费验证的 Maven/Pod/HAR 兼容组合。跨渠道契约变更同步更新配套产物，独立原生源码未变时可保留已经验证的旧版本，不为统一数字伪造新产物。发布前源码/元数据缺陷按新 RC 修正，不覆盖旧标签或归档；已经发生或未知的外部副作用须沿原 journal 只读查回，公开消费者失败不构成新建 draft、重传或再次发布同一版本的理由。
- HAR 内 README 必须包含 `ohpm install @组织/包名@版本`；prepublish 不覆盖服务端全部校验。dist-tag 由受控发布器确定：正式版使用默认 `latest`，预发布使用 `candidate-<完整版本>`；不手工固定 `next`，结果未知或标签冲突时先查回原请求，不换标签重发。进入审核不等于已上架。

## HAR 发布与消费检查点

- `prepublish` 通过只证明客户端预检。服务端还会检查作者 URL/email、命名和发布身份等字段；保留服务端原始拒绝原因，修正后按新 RC 发布，不覆盖既有 tag、归档或已提交版本。作者格式可复用：

  ```json
  {
    "author": { "name": "gycrosskit", "url": "https://github.com/gycrosskit" }
  }
  ```

- 分别记录 Maven 版本、HAR 包名/版本、保留的 Pod/tag、实际归档源码 SHA、验证 runner SHA、构建链接和摘要；同一 Release 中附件版本可以不同。仅补 checksum/验证配置的标签提交不冒充归档重建来源；未变的渠道沿用旧制品。
- 发布前核对不可变 Release 策略，在 draft 阶段一次上传并核验产物、来源和摘要。不可变 Release 公开后不能补传或增删附件；后续公开消费收据写入可编辑的发行说明、独立版本化文档或 CI artifact，不能为补证据关闭策略、覆盖标签或替换制品。初始收据仍按发布时快照解读。
- HAR-only/Native-only 标签须在共享 release Job 的对应 channel 中显式分流，不能误走要求 Maven 归档的校验；跳过其他渠道不等于本渠道消费通过，仍须独立验证实际发布包和精确消费者。
- `publish` 返回审核中、公开查询成功、精确版本安装、独立 ArkTS 消费编译是四个结果。Registry 404 时记录安装失败/编译未执行，不能把源码 HAR job 或 Maven 成功转记为 Registry 消费通过；不要反复发布同一候选催审。
- 审核期间可另建空消费者，从不可变 Release 下载 HAR、比对冻结 SHA-256，检查包身份后安装并编译公共注册/初始化 API。收据明确标为 **Release HAR 消费**；Registry 上架后仍须单独核对其下载摘要、锁文件 `resolved`/`integrity` 和实际安装路径，再从 Registry 编译。两个入口都禁止以组件源码或本地 Maven 替代。
- 使用官方 CLT 及摘要校验，在远端执行真实 Hvigor/ArkTS 编译。项目 `modelVersion` 必须匹配已选 CLT/Hvigor，不能用猜测的 SDK/API 数值代替；记录实际 Node、Hvigor、SDK/API 版本。ArkTS 与真实 Renderer 的构造器、异常类型、数据监听和 ArkUI 节点创建合同由编译与独立消费者核对，转译替身只证明其覆盖的行为。

2026-10-22 Live 复盘：旧 Maven `0.3.0-rc.1` 实际已发布，因此新 Maven 使用 `0.3.0-rc.2`；首个 HAR rc.2 虽通过 `prepublish`，仍因缺少作者 URL 被服务端 HTTP400 拒绝，修正后以 HAR `0.3.0-rc.3` 提交审核。当前组合与后续消费状态见 [Live RC Release](https://github.com/gycrosskit/live-sdk/releases/tag/0.3.0-rc.2)，不得由本段历史记录推定 Registry 或真机已通过。

## 远程验收

CI 当前入口与验证边界见[统一远程验证](统一远程验证.md)；[CI 优化与评审计划](CI优化与评审计划.md)保留旧阶段记录。`scripts/check-public-maven.py` 从[共用模板](../templates/check-public-maven.py)同步，JitPack 检查须区分状态查询与构建发起：

- 归档公开前，只查询精确版本的 JitPack 状态 API（`/api/builds/...`），保存编号原响应。`GET build.log`、POM、`.module` 或模块制品都可能触发构建，不能仅因 HTTP 方法为 GET 就宣称只读或无构建副作用；`none/building/queued` 阶段不得提前取日志或制品。
- 仅在精确版本/Tag、对应源码身份与归档已公开且字节/摘要符合冻结计划均核验后，才通过既有 readiness 入口，在 `none` 时对精确 publication POM 显式发起一次构建。`none/building/queued` 只有限等待并查询状态 API；轮询不重复发起 POM 或日志请求。真实失败、身份或 inventory 不符立即失败，不因重试放宽严格检查。
- 已确认失败的构建先保留状态原件与已取得的原始失败日志。日志取证与失败记录清理、重新构建分开处理并分别留证；取证不构成清理或重建授权，也不能用重建后的日志覆盖旧失败。永久删除失败记录须在浏览器实际执行时核对精确目标并确认；清理后仍须重新核对上述公开身份，再显式发起，不串成自动清理重建流程。

对已就绪制品的单个公开下载请求最多三次，只重试 408/429/特定 5xx、连接/读取瞬时错误与 TLS EOF；证书错误和普通 404 不重试。这不授予重复发起构建的权限。连接/读取 socket 等待 15 秒，响应读取总预算 90 秒（最后一次阻塞读取可能占用一个 socket 等待）；就绪轮询预算 300 秒，网络请求耗时另受步骤总上限约束。保留首次/历次 state、请求错误日志与最终 proof.json；错误收据不能当成 proof。上层 CI 只上传日志、JSON/JSONL、测试 XML 等小型证据，不重复上传所有下载的公开二进制。

- 在真实 JitPack 元数据逐个下载每个 variant.files，检查 size、所有声明 hash 与归档完整性；逐个检查 available-at 的真实目标及同名变体、内部依赖精确版本。APK/KLIB 编译可能不解析可选资源或来源变体，不能代替这项检查。顶层 component.url 与实际 variant 下载路径分开报告；JitPack 的 root identity 改写不能通过创建伪坐标掩盖。
- JitPack 会改写公开 POM/module，并只提供部分 sidecar。公开的 MD5/SHA-1 必须匹配实际响应；SHA-256/SHA-512 sidecar 若返回 HTTP 404，记录为渠道边界，不能声称通过这两项下载检查。变体文件声明的四种哈希仍必须全部通过；其他下载错误不能套用此边界。
- 等待目标标签的 JitPack 最终构建成功；在干净的消费工程中从 JitPack 下载并编译实际需要的 Android、iOS、OHOS 变体。只报告确实执行的检查。
- Swift Package 与 ohpm 分别验证，不能由 Maven 成功推断。ohpm 审核中或查询不到时，不写成已上架。
- 只有新远程坐标可用且旧坐标迁移完成后，才清理 `docs/maven` 及引用；新版本不默认在仓库自建 Maven 中发布。
- 发布消费者可复用本任务或默认分支已验证的只读依赖下载缓存，但保持组件 `remoteOnly`、精确版本和公开字节校验；不启用源码替换或复用测试输出。用本轮 XML/日志确认用例确实执行，不能把“测试依赖下载失败、零用例”写成测试通过。冷缓存访问上游仓库与组件自身制品是否完整分别诊断。
- 上游依赖超时或 KLIB HTTP404 时，先保留具体 URL、HTTP/连接错误和实际执行/未执行步骤；本机复核 200 不能证明 CI 所在网络已恢复。仅在瞬时故障有依据时针对原不可变版本有限重跑，保留首轮失败及每轮 runner/源码 SHA；真实缺文件、身份或摘要错误须修复，不用改版本、改仓库来源或缓存文件掩盖。最终按 job/步骤分别报告，不能把混有 Registry 404 的整条 workflow 写成通过。
- 发布凭据只存放于受控环境或本机配置，不写入 Git、日志和回答。失败时记录具体版本、产物及错误，不重用或覆盖已发布标签。

## 历史 GitHub runner 的鸿蒙 fork 仓库解析

以下保留旧 Actions 的故障定位与模板合同，不是当前 Jenkins 配置或修改 hosts 的指令。仓库使用 Eazytec Kotlin 鸿蒙 fork 时，临时 GitHub-hosted runner 可同步 `templates/ci-pin-fork-host.sh` 为项目 `scripts/ci-pin-fork-host.sh`，在 Gradle 下载前运行。该已有 helper 仅复用当前 job 经过原 HTTPS 域名验证的地址；DNS/连接失败及超时最多三次请求，DNS 错误才尝试 DoH，HTTP/TLS 错误不绕过验证；本机和 self-hosted runner 不写 hosts。同步后核对字节一致，CI 消费仍必须由真实 Gradle 解析/编译决定通过。模板信任边界用 `python3 tests/test-ci-fork-host.py` 验证，所有 hosts 写入均为替身。

若 runner 的默认地址在 TCP 建立前不可达，可由维护者设置仓库 Actions 变量 `CI_FORK_HOST_FALLBACK_IP`，workflow 同名环境变量读取；只填已经实际验证过的公网 IPv4，不将候选地址写入源码。helper 在首次 DNS/连接失败（含 `time_connect=0` 的 curl 28）后尝试该候选一次，仍验证原域名 TLS、HTTP 200 和实际 remote_ip 一致才复用；HTTP/TLS/连接后的读取超时不触发回退。未配置时保留有限重试和仅 DNS 错误的 DoH。配置候选不代表当前 DNS 答案，每个 job 都重新验证；主路径恢复后优先使用主路径，可移除该变量。Maven 和 Native LLVM 都使用同一原域名，此入口须在真实 fork Gradle 下载前运行，源码路径仅在 source=true、预热路径仅在受控 main dispatch 执行。

## Kuikly Native 链接

Kuikly Compose 的 iOS 消费者最终链接需要真实 native runtime。同步 `templates/ci-build-kuikly-render.sh` 为项目同名脚本，传入绝对构建目录；当前单参数 Renderer 探针通过官方 Pod 精确安装 OpenKuiklyIOSRender 2.29.1；Module 模式由实际 podspec 决定精确 Renderer，历史远程 Tag 保留自身依赖。两种模式均构建当前 macOS CPU 对应的 Simulator framework，验证架构及实际 context-thread 符号后输出 framework 父目录。消费者把该目录传入 linkerOpts，不能用手写占位符号或允许未定义符号代替。只有启用新 Kuikly UI 探针时执行；已冻结的 tag、Maven 资产及原生版本不因 CI 消费示例修正而覆盖。
