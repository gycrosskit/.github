# 发布流程

## 选择渠道

| 仓库 | KMP/Maven 发布 | 其他渠道 |
| --- | --- | --- |
| 14 个功能组件当前预构建版本 | macOS 构建完整 Maven 归档，校验 SHA-256 后由 JitPack 安装冻结字节 | 按组件实际提供的 SPM/Git Pod/HAR 独立验证；Maven/iOS/HAR 可采用不同配套版本。鸿蒙 Live/客服不在当前范围 |
| koin-ohos、stately-ohos、mmkv-ohos | macOS 构建版本化 Maven 归档，校验 SHA-256 后由 JitPack 安装 | 不把 GitHub Release 归档地址作为应用的 Maven 坐标 |

旧标签的原始构建方式保持不变；当前具体版本和渠道由各库顶部功能说明、发行记录与实际 `jitpack.yml` 决定。未修改渠道沿用已经验收的不可变制品，不为 14 库统一版本号空发版。ohpm 审核通过前可消费已经验证摘要和 API 的 Release HAR，不能把 Release HAR 说成 Registry 已上架。

## 发布前

1. 确认实际发布分支、提交、不可变的 Git 标签、模块坐标、Gradle 版本、Swift Package/podspec 版本、`oh-package.json5` 版本。Koin、Stately 的鸿蒙适配不在默认 `main`。
2. 按项目现有入口构建。JitPack 环境无法完成的 macOS/iOS/OHOS 构建先在相应平台完成，打包到与标签同版本的 GitHub Release；下载时校验 SHA-256，不使用可变的 `latest` 归档。
3. 检查 Maven POM、Gradle Module Metadata、平台变体和引用的 AAR/KLIB/JAR 文件。若 JitPack 把来源或 metadata 变体指向不存在的文件，先确认原因，再使用 [`jitpack-metadata.py`](../templates/jitpack-metadata.py) 模板同步所需仓库的修正脚本；不要无条件删减变体。debug-tools、customer-service 的根 `metadataSourcesElements` 也被改写为普通 JAR，与 `metadataApiElements` 地址相同但校验值不同；模板移除该来源变体，保留实际编译需要的 metadata API 与平台运行时变体。Compose 的空 Resources ZIP 也可能被 JitPack 改写为不存在的普通 ZIP；模板先检查全批 ZIP，仅在只有目录、零实际文件时裁剪资源变体及其 root available-at。即便实际文件为零字节也拒绝裁剪，必须先完成可发布的资源渠道。
4. HAR 发布前检查包内 `CHANGELOG.md` 含当前版本，执行 `assembleHar` 和 `ohpm prepublish`，再用本机受控凭据提交。`ohpm publish` 接受提交只代表进入审核；上架后还需查询并安装验证。

Native 缓存缺失或工具链变化时，先按[发布提速入口](CI优化与评审计划.md#发布提速的执行入口)在可信 main 预热；缓存仍在且 key 相同时不重复跑。发布计时分别记录本地锁等待、归档构建、PR、runner 等待、public 就绪/校验和 Android/Native consumer，不把排队时间算作编译耗时。

预构建发布候选应在创建 PR 前完成源码、版本、文档及归档 checksum 的冻结并提交。CI 按整个 PR 相对 merge-base 的差异判断源码验收；源码 PR 运行中追加 checksum 或文档提交仍会取消旧流水线并重新构建，不能当成纯文档检查。必要修复按新提交重新验收；已通过源码验收后的纯文档收尾可在合入后另开文档 PR，复用同一生产源码的既有证明，不重复构建归档。

预构建库复用 [`jitpack-install-prebuilt.sh`](../templates/jitpack-install-prebuilt.sh) 和 metadata 模板，`jitpack.yml` 传入仓库名。每个库的 `release-checksums.txt` 保存已验证的 `Tag SHA256`；未发布版本没有校验值时应直接失败，不使用假 SHA、可变归档或本地自建 Maven。metadata 修复传入当前库的路径，避免改动其他已安装组件。

本地 staging 使用空的任务目录，复用 [`check-maven.py`](../templates/check-maven.py) 检查组名、版本、精确 publication 集合、POM 许可证、平台、实际产物、大小和四种哈希。异构多模块项目显式传入完整 publication CSV；Koin/Stately 使用 `--jvm-only`，MMKV 使用 `--license BSD-3-Clause`。本地归档的 module/POM/变体文件必须具备且通过 MD5、SHA-1、SHA-256、SHA-512 sidecar 校验；SNAPSHOT 按 Maven metadata 解析时间戳文件。metadata 改写后重算 checksum；回归入口为 `python3 scripts/test-jitpack-metadata.py` 与 `python3 scripts/test-check-maven.py`。

- metadata 正规化与 checker 在 macOS 发布前执行；安装器只校验 SHA 并解包相同字节，不在 JitPack 默认的旧 Python 环境重复改写。
- macOS 归档使用 `COPYFILE_DISABLE=1 tar --no-xattrs`，核验没有 `._*` AppleDouble 成员或 xattrs，避免 Linux 把 sidecar 当 JSON。
- 预发布使用不可变 `0.x.y-rc.N`，GitHub 标记 prerelease；明确记录经消费验证的 Maven/Pod/HAR 兼容组合。跨渠道契约变更同步更新配套产物，独立原生源码未变时可保留已经验证的旧版本，不为统一数字伪造新产物。发布失败创建新 RC，不覆盖旧标签或归档。
- HAR 内 README 必须包含 `ohpm install @组织/包名@版本`；prepublish 不覆盖服务端全部校验。预发布使用 `ohpm publish --tag next`；服务端拒绝已有 dist-tag 时选择新的候选 tag 并记录，不覆盖旧候选。进入审核不等于已上架。

## 远程验收

CI 的当前阶段划分与优化验收见[CI 优化与评审计划](CI优化与评审计划.md)。scripts/check-public-maven.py 从共用模板同步：先保存编号 JitPack 原响应，再验证状态；仅 none/building/queued 有限等待，none 请求精确 publication POM 一次发起构建。真实失败、身份或 inventory 不符立即失败，不因重试放宽严格检查。

单个公开请求最多三次，只重试 408/429/特定 5xx、连接/读取瞬时错误与 TLS EOF；证书错误和普通 404 不重试。连接/读取 socket 等待 15 秒，响应读取总预算 90 秒（最后一次阻塞读取可能占用一个 socket 等待）；就绪轮询预算 300 秒，网络请求耗时另受步骤总上限约束。保留首次/历次 state、请求错误日志与最终 proof.json；错误收据不能当成 proof。上层 CI 只上传日志、JSON/JSONL、测试 XML 等小型证据，不重复上传所有下载的公开二进制。

- 在真实 JitPack 元数据逐个下载每个 variant.files，检查 size、所有声明 hash 与归档完整性；逐个检查 available-at 的真实目标及同名变体、内部依赖精确版本。APK/KLIB 编译可能不解析可选资源或来源变体，不能代替这项检查。顶层 component.url 与实际 variant 下载路径分开报告；JitPack 的 root identity 改写不能通过创建伪坐标掩盖。
- JitPack 会改写公开 POM/module，并只提供部分 sidecar。公开的 MD5/SHA-1 必须匹配实际响应；SHA-256/SHA-512 sidecar 若返回 HTTP 404，记录为渠道边界，不能声称通过这两项下载检查。变体文件声明的四种哈希仍必须全部通过；其他下载错误不能套用此边界。
- 等待目标标签的 JitPack 最终构建成功；在干净的消费工程中从 JitPack 下载并编译实际需要的 Android、iOS、OHOS 变体。只报告确实执行的检查。
- Swift Package 与 ohpm 分别验证，不能由 Maven 成功推断。ohpm 审核中或查询不到时，不写成已上架。
- 只有新远程坐标可用且旧坐标迁移完成后，才清理 `docs/maven` 及引用；新版本不默认在仓库自建 Maven 中发布。
- 发布凭据只存放于受控环境或本机配置，不写入 Git、日志和回答。失败时记录具体版本、产物及错误，不重用或覆盖已发布标签。

## GitHub runner 的鸿蒙 fork 仓库解析

仓库使用 Eazytec Kotlin 鸿蒙 fork 时，临时 GitHub-hosted runner 可同步 `templates/ci-pin-fork-host.sh` 为项目 `scripts/ci-pin-fork-host.sh`，在 Gradle 下载前运行。该已有 helper 仅复用当前 job 经过原 HTTPS 域名验证的地址；DNS/连接失败及超时最多三次请求，DNS 错误才尝试 DoH，HTTP/TLS 错误不绕过验证；本机和 self-hosted runner 不写 hosts。同步后核对字节一致，CI 消费仍必须由真实 Gradle 解析/编译决定通过。模板信任边界用 `python3 tests/test-ci-fork-host.py` 验证，所有 hosts 写入均为替身。

Kuikly Compose 的 iOS 消费者最终链接需要真实 native runtime。同步 `templates/ci-build-kuikly-render.sh` 为项目同名脚本，传入绝对构建目录；模板通过官方 Pod 精确安装 OpenKuiklyIOSRender 2.28.0，构建当前 macOS CPU 对应的 Simulator framework，验证架构及实际 context-thread 符号后输出 framework 父目录。消费者把该目录传入 linkerOpts，不能用手写占位符号或允许未定义符号代替。只有启用新 Kuikly UI 探针时执行；已冻结的 tag、Maven 资产及原生版本不因 CI 消费示例修正而覆盖。
