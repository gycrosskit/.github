# Issues 与迭代流程

真实接入项目在发生问题的组件仓库提交 Issue。组织默认的[接入问题模板](../.github/ISSUE_TEMPLATE/integration-problem.md)收集组件版本、平台、复现步骤和脱敏日志；某仓库需要专用模板时，可在该仓库覆盖默认模板。不要在公开 Issue 中提交 Token、签名文件、用户数据或完整设备标识。

## 维护流程

1. **扫描与归属**：维护任务开始时查看各组件仓库未关闭的 Issues，核对重复问题、受影响版本与平台。跨组件问题先确定最小责任仓库，相关 Issue 互相链接；信息不足时在 Issue 中追问可复现输入。
2. **复现与修复**：在独立任务分支和 Worktree 中复现问题，检查实际接入路径与全部相关调用方；只修公共根因。接入项目特有的业务逻辑留在接入项目。
3. **验证与 PR**：执行受影响平台的最小测试、构建与消费工程验证。PR 关联 Issue，列出原因、改动、验证结果和未验证平台；目标分支按[Git Flow 与提交规范](GitFlow与提交规范.md)选择，检查通过后合并。
4. **发布与回归**：需要新远程版本的修复按[发布流程](发布流程.md)创建不可变标签，分别确认 JitPack、Swift Package、ohpm 中实际使用的渠道，再由真实接入项目验证。PR 合并或 `ohpm publish` 已提交，都不等于用户拿到了可用版本。
5. **关闭 Issue**：在 Issue 中记录修复 PR、版本、远程坐标和接入验证结果后关闭。若代码已合并但版本尚未可用，保持 Issue 开放并说明发布进度；文档类问题可在已合并且验证后直接关闭。回归问题重新打开或链接新 Issue。

新仓库应启用 Issues 并提供反馈入口。AI 可以按此流程扫描和处理 Issues；周期性无人值守扫描需要另行配置运行频率、执行环境和通知方式，本文件本身不会启动定时任务。
